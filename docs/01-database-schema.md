# Database Schema

PostgreSQL 17 with PostGIS 3.5 (see [AI Development Notes](05-ai-development-notes.md#database-connections) for connection details). The PostGIS extension is available in the Docker image but is not enabled yet; it will be created in a migration when the first spatial table is added.

The planned donation schema is described in [Planned Features](06-planned-features.md#planned-schema). This document lists only the tables that currently exist.

## Current Tables

Laravel's default migrations were removed so that every migration in this project is generated with `php artisan make:migration` and carries the timestamp of when it was created (see [Migration Generation](05-ai-development-notes.md#migration-generation)). Framework tables are generated with their own Artisan commands (see [Framework Tables](#framework-tables)); a password reset table comes with donor accounts (milestone 9).

### users

Donors and administrators. Model: `App\Models\User`. Donors are created automatically from the email address entered on the donate page, with no password. The table holds donors' personal contact details; never copy its rows into the repository, issues, or chat.

| Column | Notes |
|--------|-------|
| name | Nullable |
| email | Unique, including among soft-deleted users, so a deleted account keeps its address reserved. Stored lowercase by the model, so finding a user by email is case-insensitive |
| email_verified_at | Nullable timestamp |
| password | Nullable; hashed by the model. Admins' passwords are set with [users:admin](02-services-and-commands.md#usersadmin-appconsolecommandsmanageadminphp), at least 12 characters. Donors can always sign in with an email link once accounts are built |
| role | String, default `donor`: `donor` or `admin` (`User::ROLES`). Board members are given `admin` until they need different permissions. Not mass assignable, so form input can never change it; admins are made with `users:admin` |
| remember_token | Nullable |
| created_at, updated_at | |
| deleted_at | Nullable; soft deletes (see [Deletion](06-planned-features.md#deletion)) |

A user with **transaction history** cannot be deleted, soft or hard: `delete()` and `forceDelete()` throw a `LogicException`. `hasTransactionHistory()` is true when the user has any received donation (`succeeded`, `refunded`, or `partially_refunded`), including a soft-deleted one. Soft-deleting a user without it, such as a spam account from a carding attack, also soft-deletes their donations (all failed or pending), checkouts, and subscriptions, keeping them out of reports. Restoring the user does not restore those. Hard deletes are deliberate one-offs, which foreign keys refuse while any related row remains.

### designations

What a donor directed their donation toward (see [Designations](06-planned-features.md#designations)). Model: `App\Models\Designation`.

| Column | Notes |
|--------|-------|
| name | |
| slug | Unique, including among soft-deleted designations, so a slug always means the same fund. Travels in gateway metadata |
| description | Nullable |
| is_restricted | Boolean, default false. Donations to restricted designations can only be spent on them |
| is_active, sort_order | Boolean (default true) and integer (default 0), for the future donate-page selector |
| created_at, updated_at | |
| deleted_at | Nullable; soft deletes |

The **General Fund** (`general-fund`, unrestricted) is inserted by the table's migration rather than a seeder, because deploys run migrations but never seeders. `Designation::generalFund()` returns it. Checkouts, subscriptions, and donations created without a designation are assigned it automatically (`App\Models\Traits\BelongsToDesignation`), including payments imported from outside our donation flow.

### donations

One row per payment, one-time or from a recurring donation, including failed payments. Model: `App\Models\Donation`.

| Column | Notes |
|--------|-------|
| user_id, designation_id | Foreign keys; restrict deletes. The designation defaults to the General Fund |
| subscription_id | Nullable foreign key; set for payments of a recurring donation |
| checkout_id | Nullable foreign key; set for payments started on our donate page |
| gateway, gateway_payment_id | Unique together, including among soft-deleted rows; the Stripe PaymentIntent. A payment received through several webhook events, a retried webhook, or a re-import is one row |
| gateway_invoice_id | Nullable; set for subscription payments. Indexed |
| amount_cents | Integer |
| fee_cents | Nullable integer; the gateway's processing fee, once known |
| refunded_cents | Integer, default 0 |
| currency | Lowercase ISO code as the gateway sends it, default `usd` |
| status | String: `pending`, `succeeded`, `failed`, `refunded`, or `partially_refunded` (`Donation::STATUSES`). Indexed |
| paid_at | Nullable timestamp |
| gateway_data | Nullable JSONB copy of the latest gateway object |
| created_at, updated_at | |
| deleted_at | Nullable; soft deletes |

A **received** payment is one we actually collected, even if it was refunded later: `succeeded`, `refunded`, or `partially_refunded` (`Donation::RECEIVED_STATUSES`, the `received()` scope, and `wasReceived()`). Received payments make up a user's transaction history.

### subscription_events

The history of each recurring donation in our own vocabulary, independent of the gateway. Model: `App\Models\SubscriptionEvent`. Append-only: there is no `deleted_at`, and the model throws a `LogicException` on any update or delete.

| Column | Notes |
|--------|-------|
| subscription_id | Foreign key; restricts deletes. `$subscription->events` lists them oldest first |
| type | String: `created`, `renewed`, `payment_failed`, `amount_changed`, `paused`, `resumed`, `canceled`, or `reactivated` (`SubscriptionEvent::TYPES`) |
| source | String: `webhook`, `import`, `admin`, or `donor` (`SubscriptionEvent::SOURCES`) |
| source_reference | The event, invoice, or action that caused it. Unique together with `subscription_id` and `type`, so sync code records events with `firstOrCreate()` on those three columns and a re-import never duplicates history |
| occurred_at | Timestamp |
| data | Nullable JSONB |
| created_at, updated_at | |

### webhook_events

Every incoming payment gateway webhook, stored before it is processed on the queue, for deduplication, debugging, and replay. Model: `App\Models\WebhookEvent`. Append-only: only the processing status changes after an event is stored, there is no `deleted_at`, and the model throws a `LogicException` on delete.

| Column | Notes |
|--------|-------|
| gateway, event_id | Unique together, so a redelivered event is stored once |
| type | The gateway's event type, such as `checkout.session.completed`. Indexed |
| payload | JSONB; the event as received |
| processed_at | Nullable timestamp; set once processing succeeds (`isProcessed()`) |
| attempts | Integer, default 0 |
| error | Nullable text; the last processing failure |
| created_at, updated_at | |

### donation_receipts

Tax receipts sent to donors. Model: `App\Models\DonationReceipt`. Issued and sent by `DonationReceipts` (see [Services & Commands](02-services-and-commands.md#donationreceipts-appservicesdonationreceiptsphp)).

| Column | Notes |
|--------|-------|
| user_id | Foreign key; restricts deletes |
| donation_id | Nullable foreign key; set for receipts for a single donation. At most one `single` receipt per donation, including soft-deleted receipts: a partial unique index (`donation_receipts_single_donation_unique`) makes the database refuse a second one |
| receipt_number | `WET-<tax year>-<random code>`, such as `WET-2026-K7Q2MX`. Random rather than sequential, so it reveals nothing about how many donations we receive. Unique, including among soft-deleted receipts, so a number is never reused |
| type | String: `single` or `annual_summary` (`DonationReceipt::TYPES`) |
| tax_year, amount_cents | Integers. The tax year is the year the donation was paid in Fort Collins time |
| sent_at | Nullable timestamp; set once the email is sent. A receipt issued but not sent, such as after an email failure, is sent on the next try |
| created_at, updated_at | |
| deleted_at | Nullable; soft deletes |

### Finding Records by Gateway ID

Models synced from a payment gateway use `App\Models\Traits\HasGatewayId`. `findByGatewayId($gateway, $id)` looks a record up by the gateway's own ID, including soft-deleted rows, so receiving the same object again updates its record without restoring it and never creates a duplicate (see [Payment Sync and Import](06-planned-features.md#payment-sync-and-import)). Each model names its ID column in `GATEWAY_ID_COLUMN`: `gateway_customer_id` for gateway customers, `gateway_session_id` for checkouts, `gateway_subscription_id` for subscriptions, and `gateway_payment_id` for donations.

### leaf_applications

Requests to donate leaves to the leaf program, by drop-off or pickup. Model: `App\Models\LeafApplication`. The table holds donors' personal contact details, which are never shared; never copy its rows into the repository, issues, or chat.

| Column | Notes |
|--------|-------|
| type | String: `drop_off` or `pickup` (`LeafApplication::TYPES`) |
| name | |
| email | Stored lowercase by the model, so finding a donor's applications by email is case-insensitive |
| phone | |
| address | Up to 500 characters; where the leaves are coming from |
| estimated_bag_count | Integer; the donor's estimate, since many don't know the exact count in advance. Large counts may need a special pickup trip, while small ones are batched with other pickups |
| ready_now | Boolean; whether the bags are ready now |
| ready_date | Nullable date, set when the bags are not ready yet: when they will be, the soonest they can be picked up or dropped off. Donors never choose a pickup date or time; we schedule pickups around routes and volunteers |
| referral_source | Nullable text; how the donor heard about us |
| questions | Nullable text |
| terms_accepted_at | Timestamp; when the donor agreed to the program's terms |
| created_at, updated_at | |
| deleted_at | Nullable; soft deletes. Deleted applications are kept but hidden, including from `leaves:applications`; `leaves:view` still shows one by its ID, marked as deleted (see [Deletion](06-planned-features.md#deletion)) |
| contact_id | Nullable foreign key; restricts deletes. The person who applied, linked by `ContactLinker` after the application is saved, or by [contacts:link](02-services-and-commands.md#contactslink-appconsolecommandslinkcontactsphp) for earlier ones (see [contacts](#contacts)). Null until linked, or while an application that matches more than one contact with the same name waits for review. The application keeps its own name, email, phone, and address as submitted |
| contact_review | Nullable JSONB list of why linking needs an admin to look (`LeafApplication::REVIEW_REASONS`): `address` (the contact it was linked to has a different current address), `shared_email` or `shared_phone` (its email or phone number is also on another contact, such as two people sharing a phone, or the same person with a name written differently), or `conflict` (it matches more than one contact with the same name, so it isn't linked). Null when nothing needs a look. `needsContactReview()` and the `needingContactReview()` scope find those not reviewed yet |
| contact_reviewed_at, contact_reviewed_by | Nullable timestamp, and a nullable foreign key to `users` that restricts deletes: when and by which admin the review was done (`$application->contactReviewer`), by marking it reviewed or moving it to a contact on the application's admin page (see [ApplicationReview](02-services-and-commands.md#applicationreview-appservicesapplicationreviewphp)). Set only there, never from form input. The reasons stay in `contact_review` as a record of why it was flagged |

### contacts

People we keep in touch with, starting with those who apply to donate leaves (see [Leaf Application CRM](06-planned-features.md#leaf-application-crm)). Model: `App\Models\Contact`. Holds names and standing notes about people; never copy its rows into the repository, issues, or chat.

| Column | Notes |
|--------|-------|
| name | The only thing a contact needs |
| notes | Nullable text; standing information, such as "prefers texts after 5pm" |
| created_at, updated_at | |
| deleted_at | Nullable; soft deletes. Deleted contacts aren't matched by new applications |
| merged_into_id | Nullable foreign key to `contacts`; restricts deletes. Set when the contact was merged into another and deleted (see [ContactMerger](02-services-and-commands.md#contactmerger-appservicescontactmergerphp)), so its page sends admins to that one (`$contact->mergedInto`) |

`$contact->applications` are their leaf applications, and `$contact->details` all their emails, phone numbers, and addresses. `primary($type)` is the primary current email or phone number, and `address()` the current address. Change details through `usePrimary($type, $value)`, which makes an email or phone number primary, putting a matching one back in use rather than adding a copy, and `moveTo($value)`, which makes an address current and marks the previous one removed; `addDetail($type, $value)`, which adds an email or phone number, or puts a matching one back in use, as primary only when there's no primary one yet (an address goes through `moveTo()`); and `removeDetail($detail)`, which marks a detail removed and, when it was the primary one, makes the most recently added current one of its type primary. `findDetail($type, $value)` finds the contact's detail with the same normalized value, current or removed.

### contact_details

A contact's emails, phone numbers, and address, several per contact. Model: `App\Models\ContactDetail`. Holds personal contact details; never copy its rows into the repository, issues, or chat.

| Column | Notes |
|--------|-------|
| contact_id | Foreign key; restricts deletes |
| type | String, up to 20 characters: `email`, `phone`, or `address` (`ContactDetail::TYPES`) |
| value | Up to 500 characters, as entered, trimmed |
| normalized | Nullable, up to 500 characters; set from the value on every save (`ContactDetail::normalize()`), for matching: an email trimmed and lowercase; a US phone number's 10 digits, without a leading country code 1; an address lowercase, with commas and periods as spaces and spacing collapsed. Null when there's nothing to match on, such as a phone number without an area code, which is kept but never matched. Indexed together with `type` |
| label | Nullable, up to 50 characters, such as "mobile" |
| is_primary | Boolean, default false. The one to use for each type |
| removed_at | Nullable timestamp; set when a detail is no longer in use, such as a previous address. Removed details are kept, so matching still finds a previous number or address, and are never deleted |
| created_at, updated_at | |

A contact has **one current address**, and at most **one current primary detail of each type**; partial unique indexes make the database refuse a second (`contact_details_one_current_address` and `contact_details_one_primary`). Addresses will hold their map location (milestone step 3).

### form_submissions

Every submission of the donate and leaf application forms, recorded the moment it arrives, before validation or anything else can fail, so a visitor who hits an error can still be reached. Model: `App\Models\FormSubmission`; recorded by the `RecordFormSubmission` middleware (see [Form Submissions](03-routes-and-controllers.md#form-submissions)). Holds visitors' names, emails, and form details, including from submissions that failed; never copy its rows into the repository, issues, or chat. Kept permanently.

| Column | Notes |
|--------|-------|
| reference | Six random characters without the lookalikes 0, 1, I, L, and O, such as `F7K2QX`. Unique. Shown to the visitor with any error, so a visitor who emails us can be matched to their submission |
| form | String: `donation` or `leaf_application` (`FormSubmission::FORMS`). Indexed |
| name, email | Nullable; as typed, even if invalid. The email is trimmed and lowercased. Email is indexed |
| data | Nullable JSONB: the other fields as submitted, never the CSRF or proof-of-work tokens. At most 30 fields of up to 5,000 characters each, since anyone can submit anything |
| outcome | String, default `received` (`FormSubmission::OUTCOMES`): `received` (nothing recorded yet; one left this way stopped without an outcome), `rejected` (by the form's rules), `expired` (the page had expired, a 419), `rate_limited`, `unavailable` (online donations not configured), `payment_error` (the payment processor couldn't be reached), `error` (a server error), `sent_to_payment`, or `saved`. Indexed |
| errors | Nullable JSONB: the messages the visitor was shown, by field |
| checkout_id | Nullable foreign key; the checkout a donation started. Its status shows whether the donor finished paying |
| leaf_application_id | Nullable foreign key; the application saved |
| user_agent | Nullable, up to 500 characters; the visitor's browser and device |
| resolution | Nullable string, up to 20 characters; how an admin closed a submission that needs no more follow-up, on the Error Logs pages: `resolved` (we followed up with the visitor), `test` (someone testing the form), or `spam` (such as a bot filling in the form). Null while it's open. Spam and tests are left out of Error Logs unless asked for, and no closed submission is counted on the dashboard |
| resolved_at | Nullable timestamp, indexed; when it was closed |
| resolved_by | Nullable foreign key to `users`; restricts deletes. The admin who closed it |
| resolution_note | Nullable text, up to 1,000 characters from the form; the admin's note, such as "Called them back." The four resolution columns are set only by `close()` and cleared by `reopen()`, never from form input. They replaced the earlier `marked_spam_at` and `marked_spam_by`, whose marks became `spam` |
| created_at, updated_at | `created_at` is indexed |

**Follow-ups:** a submission that didn't go through is **resolved** when the same visitor later submitted the same form successfully: a `saved` leaf application, or a donation `sent_to_payment` whose checkout completed. The same visitor means the same email address, or for leaf applications the same phone number once its spelling is normalized (`phoneDigits()`: digits only, without a leading US country code). There is no time limit, so a visitor who came back days later counts, and Error Logs says how long after. One with no such submission, and not closed by an admin, is **unresolved**. An admin's closing comes first: a submission closed as resolved shows that, even if the visitor also came back. `FormSubmissionReport` finds these (see [Report Classes](02-services-and-commands.md#report-classes-appreports)); nothing is stored. `$submission->donation` is the donation a submission's checkout paid for.

## Framework Tables

Tables Laravel's own features use, generated unchanged from the framework's stubs. They hold little personal data of their own: a queued job's payload can include the records it works on, and a session records the visitor's IP address, browser, and, once signed in, their user ID.

| Tables | Generated with | Used by |
|--------|----------------|---------|
| `cache`, `cache_locks` | `php artisan make:cache-table` | The `database` cache store: proof-of-work challenges already used, `queue:restart` signals, and rate limits, such as failed sign-in attempts |
| `jobs` | `php artisan make:queue-table` | The `database` queue: jobs waiting for the queue worker |
| `failed_jobs` | `php artisan make:queue-failed-table` | Jobs that failed, kept for `queue:retry` (see [Operating a Server](07-deployment.md#operating-a-server)) |
| `sessions` | `php artisan make:session-table` | The `database` session driver: every visitor's session, including who is signed in |

## Framework Drivers

The drivers set in `laravel/.env.example`. A driver switches to `database` once its tables exist:

| Setting | Value | Notes |
|---------|-------|-------|
| `CACHE_STORE` | `database` | Uses the `cache` and `cache_locks` tables |
| `QUEUE_CONNECTION` | `database` | Uses the `jobs` and `failed_jobs` tables; the `queue` container runs the jobs |
| `SESSION_DRIVER` | `database` | Uses the `sessions` table. Servers switched from `file` by hand when sign-in was added (see [Server Settings](07-deployment.md#server-settings)) |

Tests use in-memory stores instead (`array` for the cache and sessions, `sync` for the queue), set in `phpunit.xml`.

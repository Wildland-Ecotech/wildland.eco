# Deployment

## Local Development

### Laravel (Docker)

The Docker environment was generated by [Wetfish Skeleton](https://github.com/wetfish/skeleton). The same `docker-compose.yml` runs locally, on staging, and in production:

| Service | Image | Purpose |
|---------|-------|---------|
| app | php:8.5.12-fpm (custom `Dockerfile`) | PHP-FPM with Laravel extensions and Composer |
| queue | Same as app | Runs queued jobs with `php artisan queue:work`. Exits after an hour or when signaled by `queue:restart`, and Docker starts it again |
| scheduler | Same as app | Runs the tasks scheduled in `routes/console.php` with `php artisan schedule:work` |
| nginx | nginx:alpine | Serves `laravel/public/`, proxies PHP to app |
| db | postgis/postgis:17-3.5 | PostgreSQL 17 + PostGIS 3.5 |
| db-test | postgis/postgis:17-3.5 | Disposable test database; local development only (the `testing` profile), with its data kept in memory |
| stripe | stripe/stripe-cli:v1.55.1 | Forwards Stripe test mode events to the webhook endpoint; local development only (the `stripe` profile). See [Stripe](#stripe) |
| node | node:24-slim | Builds frontend assets; runs on demand with `docker compose run --rm node`, never as a long-running container |

Published ports are bound to `127.0.0.1`, so the site and database are reachable only from the machine itself. On servers, a reverse proxy handles public traffic.

Configuration is split across two gitignored files:

- **Root `.env`:** Docker settings (container name prefix, ports, user and group IDs, database credentials, and on servers the deploy branch). Copy from `.env.example`.
- **`laravel/.env`:** Laravel settings. Copy from `laravel/.env.example`. `DB_PASSWORD` must match the root `.env`.

First-time setup from a fresh clone:

```bash
cp .env.example .env
cp laravel/.env.example laravel/.env
docker compose up -d
docker compose exec app composer install
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
docker compose run --rm node npm ci
docker compose run --rm node npm run build
```

Set a real `DB_PASSWORD` in both `.env` files before the first `docker compose up`, because PostgreSQL stores the password when the database volume is created. The site is served at `http://localhost:8080` (or the `NGINX_PORT` in the root `.env`).

The `queue` and `scheduler` containers restart until `composer install` has created `laravel/vendor` and the migrations have created the queue tables; after that they run on their own. Their output is in `docker compose logs -f queue scheduler`.

Set `UID` and `GID` in the root `.env` to your user's IDs (`id -u` and `id -g`) so files created by the containers stay editable.

Rebuild assets with `docker compose run --rm node npm run build` after changing styles or scripts. For hot reloading, run `npm run dev` in `laravel/` with Node installed on the host; running the Vite dev server in Docker is not set up yet.

### Stripe

Payments are disabled until `STRIPE_SECRET` is set in `laravel/.env`. Local development and staging always use Stripe's **test mode**; only production (`APP_URL` `https://wildland.eco`) may use live mode keys, and `stripe:check` enforces it (see [Services & Commands](02-services-and-commands.md#stripecheck-appconsolecommandscheckstripeconfigurationphp)).

| Setting | Value |
|---------|-------|
| `STRIPE_SECRET` | A test mode secret key (`sk_test_`) from the Stripe dashboard |
| `STRIPE_WEBHOOK_SECRET` | Locally, the signing secret the Stripe CLI prints (`whsec_`); on servers, the signing secret of that server's webhook endpoint |
| `STRIPE_DONATION_PRODUCT_ID` | The ID (`prod_`) of the "Donation" product in that mode |
| `STRIPE_PORTAL_LOGIN_URL` | The Customer Portal's no-code login link in that mode |

Stripe cannot reach `localhost`, so locally the **Stripe CLI** forwards test mode events over the Docker network. It runs in the `stripe` profile, which is never started unless named, and it refuses to start without a test mode key:

```bash
docker compose --profile stripe up -d stripe
docker compose logs stripe
```

Copy the signing secret from its output (`Your webhook signing secret is whsec_...`) into `STRIPE_WEBHOOK_SECRET`. It stays the same between restarts.

Once started, the CLI comes back after a reboot, like the other services, until it is stopped. Events that happen while it isn't running are never forwarded: the CLI isn't a registered endpoint, so Stripe doesn't retry them.

The CLI forwards only the events the payment sync handles, from your own account, listed in `STRIPE_EVENTS` in `docker-compose.yml`. The webhook endpoints registered for staging and production subscribe to the same events, so when the list changes, update the endpoints in the Stripe dashboard too. Stop the CLI with `docker compose --profile stripe stop stripe`.

The Stripe CLI is for local development only, and three things keep it off the servers:

- Servers never enable the `stripe` profile (`COMPOSE_PROFILES=server`), so deploys never create the container or pull its image.
- `deploy/deploy.sh` refuses to deploy if `COMPOSE_PROFILES` includes `stripe`.
- Every deploy removes a Stripe CLI container if one exists, such as one started by hand with `--profile stripe`, and logs that it did. To remove one right away, deploy by hand (`sudo systemctl start wildland-deploy`).

The CLI also refuses to start without a test mode key, so it can never connect to live mode.

Forwarded events are processed by the queue worker. `docker compose logs stripe` shows each delivery and its response (`[200]`), and `docker compose logs queue` shows the processing job. The worker keeps the code it started with, so after changing PHP files locally, restart it with `docker compose exec app php artisan queue:restart` (deploys do this on servers).

To bring in payments made while nothing was listening, such as before the CLI started, run the importer: `docker compose exec app php artisan stripe:sync` (see [stripe:sync](02-services-and-commands.md#stripesync-appconsolecommandssyncstripephp)).

**Servers** receive events from a webhook endpoint registered in that server's Stripe sandbox (staging) or live account (production), in Workbench → Webhooks → **Create an event destination**:

1. Events from **Your account**, with the **Snapshot** payload, and the API version set to our pinned version (`services.stripe.api_version` in `config/services.php`).
2. The events listed in `STRIPE_EVENTS` in `docker-compose.yml`.
3. A **Webhook endpoint** at `https://<server's APP_URL host>/webhooks/stripe`: `https://stage.wildland.eco/webhooks/stripe` or `https://wildland.eco/webhooks/stripe`.
4. Copy the endpoint's signing secret (**Reveal secret**) into that server's `STRIPE_WEBHOOK_SECRET`, then deploy by hand (`sudo systemctl start wildland-deploy`) so the configuration is cached again.

Stripe shows each delivery under the endpoint's **Event deliveries**, and a stored copy of every event is in the `webhook_events` table. Secrets can be rolled from the endpoint's ⋯ menu, keeping the old one valid for up to 24 hours while the server's `.env` is updated.

The containers set `STRIPE_SUPPRESS_NOTICES=true`. The Stripe SDK turns informational notices from Stripe into PHP warnings, which Laravel throws as exceptions, so a notice would fail an API call that had already succeeded. The SDK reads the setting from the process environment, not `laravel/.env`, so it is set in `docker-compose.yml`.

### Email

Email is sent through [AhaSend](https://ahasend.com/docs/smtp) over SMTP: `send.ahasend.com`, port 587, upgraded to TLS with STARTTLS. The site refuses to send over an unencrypted connection (`require_tls` in `config/mail.php`), so the SMTP password never travels in the clear. Emails come from `no-reply@from.wildland.eco`, and replies go to `contact@wildland.eco`. AhaSend only sends from the sending domain verified in its account, `from.wildland.eco`, with its SPF, DKIM, and DMARC records; a from address on any other domain, including `wildland.eco` itself, is refused with `556 Invalid account. Tenant or Domain not found`. The reply-to address can be on any domain.

AhaSend SMTP credentials come in two modes, set on each credential in the AhaSend dashboard (Credentials):

- **Sandbox:** AhaSend checks and records each message in its dashboard, but never delivers it or uses credits. Use one locally, so testing can never email a real person.
- **Live:** messages are delivered. Production uses one. Staging can use either; a live one delivers to the email addresses used in test donations.

| Setting | Value |
|---------|-------|
| `MAIL_MAILER` | `smtp` to send through AhaSend; `log` writes each email to `storage/logs/laravel.log` instead, which is the default in `laravel/.env.example` |
| `MAIL_HOST`, `MAIL_PORT` | `send.ahasend.com`, `587` |
| `MAIL_USERNAME`, `MAIL_PASSWORD` | The SMTP credential's username and password, created per environment |
| `MAIL_FROM_ADDRESS`, `MAIL_FROM_NAME` | `no-reply@from.wildland.eco`, `Wildland Ecotech`. The address must be on `from.wildland.eco` |
| `MAIL_REPLY_TO_ADDRESS` | `contact@wildland.eco` |

Check the settings by sending a test email, which is sent right away rather than queued (see [mail:test](02-services-and-commands.md#mailtest-appconsolecommandssendtestemailphp)):

```bash
docker compose exec app php artisan mail:test you@example.com
```

With a sandbox credential, the message then appears in the AhaSend dashboard without being delivered.

### Running Tests

Tests run against the `db-test` service, a separate PostgreSQL + PostGIS database from the same image as production, never SQLite or the development database. It belongs to the `testing` profile, so `docker compose up` does not start it and servers never run it. Start it once; it restarts with Docker:

```bash
docker compose --profile testing up -d db-test
docker compose exec app php artisan test
```

Its data is kept in memory and discarded whenever the container stops, and tests that use the database migrate it from scratch. `phpunit.xml` points the database settings at `db-test`, and `tests/TestCase.php` stops every test before it touches a database if the connection is anything else, for example when the configuration is cached (run `docker compose exec app php artisan config:clear`).

### Updating PHP

The `Dockerfile` pins an exact PHP release (`php:8.5.12-fpm`) rather than the floating `8.5-fpm` tag. Deploys run `docker compose build` without `--pull`, so a floating tag can keep using an older cached image after a security release. Pinning means each update is a reviewed commit, and a deploy always rebuilds with the new version.

When [php.net](https://www.php.net/) announces a release for the 8.5 branch, especially a security release:

1. Check that the official image tag (for example `php:8.5.13-fpm`) is published on [Docker Hub](https://hub.docker.com/_/php).
2. Update the `FROM` line in the `Dockerfile` and the app row in the table above.
3. Rebuild locally and check the version:

```bash
docker compose build app
docker compose up -d
docker compose exec app php -v
docker compose --profile testing up -d db-test
docker compose exec app php artisan test
```

Merging into `main` and `release` deploys it: the deploy rebuilds the changed image and recreates the app container, with no manual step on the servers.

### Updating the Stripe API version

Stripe structures every request, response, and webhook event by an API version. Ours is pinned in two places that must change together: the Stripe PHP SDK (`stripe/stripe-php` in `composer.json`), whose generated code matches one version, and `services.stripe.api_version` in `config/services.php`, which every request sends as its `Stripe-Version`. Stripe releases a compatible version monthly and a major version with breaking changes twice a year (such as `dahlia` to `endive`); see [How API versioning works](https://docs.stripe.com/api-versions).

Three other things in Stripe have a version of their own:

| Where | Used for | Set in |
|-------|----------|--------|
| Each account's or sandbox's **default API version** | Events the Stripe CLI forwards, events fetched through the API, and requests without a `Stripe-Version` | Workbench → Overview, or Settings → Developers → Preferences. An upgrade can be reverted for a few days |
| Each **webhook endpoint** | The payloads of the events sent to it | Chosen when the endpoint is created |
| The **Stripe CLI** | Its own requests, and the events it forwards | The account default; `stripe listen --latest` would use the newest version instead, which can move ahead of ours, so it isn't used |

To move to a new version:

1. Read the [API changelog](https://docs.stripe.com/changelog.md) from our version to the new one, and the SDK's `CHANGELOG.md`. Within one major version (the name after the date), changes are compatible; across majors, check every field the code uses.
2. Update the SDK and set `api_version` to the version that SDK release pins (`Stripe\Util\ApiVersion::CURRENT` in `vendor/stripe/stripe-php/lib/Util/ApiVersion.php`), then run the tests:

```bash
docker compose exec app composer require stripe/stripe-php:^<major>.0
docker compose exec app php artisan test
```

3. Upgrade the local development sandbox's default API version, and restart the Stripe CLI. Its banner (`docker compose logs stripe`) shows the version it forwards.
4. For each server's sandbox or account, upgrade the default API version, and move its webhook endpoint to the new version. Within a major version, edit the endpoint's version. Across majors, follow Stripe's [webhook versioning](https://docs.stripe.com/webhooks/versioning.md) guide: create a second endpoint at the new version, run both until the new code is deployed, then remove the old one.

The webhook handler logs a warning for any event whose `api_version` differs from ours, so a version left behind shows up in the logs.

## Servers

Staging and production each run on their own server from a clone of the repository, using the same `docker-compose.yml` as local development. The clone can be in any directory; deploys run as the user who owns it. Two more services run only on servers, enabled by `COMPOSE_PROFILES=server`:

| Service | Purpose |
|---------|---------|
| caddy | Terminates HTTPS on ports 80 and 443, obtains and renews certificates automatically, and forwards requests to nginx. Configured by `deploy/caddy/<CADDY_SITE>.Caddyfile`. |
| webhook | Receives GitHub push webhooks at `/hooks/deploy`. It verifies the signature, and for pushes to the server's branch writes `deploy/trigger/deploy-requested`. It has no Docker access, and its port (9000) is reachable only by Caddy over Docker's internal network. |

### How Deploys Work

1. Every push sends a webhook to `https://<server hostname>/hooks/deploy` on each server. Caddy receives it on the standard HTTPS port and forwards it to the webhook container; no other port needs to be opened.
2. The webhook container checks the `X-Hub-Signature-256` signature against `WEBHOOK_SECRET`, then compares the pushed branch with `DEPLOY_BRANCH`. GitHub shows the response under the webhook's Recent Deliveries:
   - **Push to the server's branch:** 200, "Deploy of `<branch>` requested".
   - **Push to another branch, or GitHub's ping:** 200, "Ignored `<ref>`", without deploying.
   - **Wrong signature** (the secrets in GitHub and the root `.env` differ): 500.
   - **No signature** (not sent by GitHub with a secret): 403.

   Every failed delivery therefore points to a real problem.
3. A signed push to the server's branch writes the trigger file. The `wildland-deploy.path` systemd unit on the host sees the change and starts `wildland-deploy.service`, which runs `deploy/deploy.sh` as the clone's owner.
4. `deploy/deploy.sh` checks out the branch's latest commit, rebuilds and restarts containers, reloads the Caddy config, installs PHP dependencies without dev packages, builds assets, runs migrations, caches configuration, routes, and views, restarts the queue worker with `php artisan queue:restart` so it picks up the new code, and runs `php artisan stripe:check`, which fails the deploy if the Stripe keys are for the wrong mode. The scheduler starts a new process for each run, so it needs no restart. If more commits arrived during the deploy, it deploys again.

Deploys in the same environment never overlap. The clone is used only for deploys: the script discards local changes to tracked files, while untracked files such as `.env` and `laravel/.env` are kept. To deploy a different branch, see [Switching Branches](#switching-branches).

### Server Settings

| File | Setting | Staging | Production |
|------|---------|---------|------------|
| Root `.env` | `COMPOSE_PROFILES` | `server` | `server` |
| Root `.env` | `CADDY_SITE` | `staging` | `production` |
| Root `.env` | `DEPLOY_BRANCH` | `main` | `release` |
| Root `.env` | `WEBHOOK_SECRET` | Random, unique per server | Random, unique per server |
| `laravel/.env` | `APP_ENV` | `production` | `production` |
| `laravel/.env` | `APP_DEBUG` | `false` | `false` |
| `laravel/.env` | `APP_URL` | `https://stage.wildland.eco` | `https://wildland.eco` |
| `laravel/.env` | `STRIPE_*` | Test mode keys and IDs | Live mode keys and IDs |
| `laravel/.env` | `MAIL_USERNAME`, `MAIL_PASSWORD` | AhaSend SMTP credential, sandbox or live | Live AhaSend SMTP credential |

Staging uses `APP_ENV=production` so it behaves exactly like production. Each server gets its own `APP_KEY`, database password, and webhook secret.

### Setting Up a Server

`deploy/setup.sh` sets up a server in one run, from a clone of the repository. It needs a Debian or Ubuntu server with sudo access, and its domains (below) already pointing at it so Caddy can obtain the HTTPS certificate.

Clone the repository into any directory, then run the script:

```bash
sudo apt install git
git clone https://github.com/Wildland-Ecotech/wildland.eco.git
cd wildland.eco
sudo deploy/setup.sh
```

The script asks for:

- **Environment:** `staging` or `production`
- **Branch to deploy:** defaults to `main` for staging and `release` for production. If the branch does not exist on GitHub yet, or does not contain the Laravel site, the script says so and asks again.
- **AhaSend SMTP username and password:** optional; without them, email is written to the Laravel log (see [Email](#email))

It then:

1. Makes sure the clone has a non-root owner. Deploys and containers run as the clone's owner, and the containers must not run as root: PHP-FPM started as root serves requests as `www-data`, which cannot write to root-owned storage. If the clone is owned by root (for example, cloned into `/opt` as root), the script creates a `deploy` user with no password or login shell and gives it the clone.
2. Installs Docker Engine with the Compose plugin from Docker's apt repository.
3. Adds the clone's owner to the `docker` group, since deploys run as that user. Membership in the `docker` group is equivalent to root access.
4. Writes both `.env` files from their examples with the server settings, generating the database password, `APP_KEY`, and webhook secret. Both files are readable only by the clone's owner.
5. Runs the first deploy, which builds the containers, obtains the HTTPS certificate, and sets up the database.
6. Installs the systemd units that run deploys when the webhook fires, with the clone's path and owner filled in. They are copied rather than linked, so a deploy can never change the host's services.
7. Prints the settings for the GitHub webhook.

The one manual step is adding the webhook in GitHub (repository Settings → Webhooks → Add webhook) with the printed payload URL, content type, and secret, for push events only. GitHub's first test ping should succeed with an "Ignored" response; a 500 means the secret does not match.

The script is safe to re-run. It keeps existing `.env` files (updating only the container user IDs if the clone's owner changed) and repeats the remaining steps, so re-running it after the systemd units change in the repository installs the new versions.

### Operating a Server

```bash
# Deploy the latest commit by hand
sudo systemctl start wildland-deploy

# Follow deploy output
journalctl -u wildland-deploy -f

# Webhook and Caddy logs (from the clone's directory)
docker compose logs -f webhook caddy

# Queue worker and scheduler logs
docker compose logs -f queue scheduler

# Output of the nightly Stripe sync, one line per object
tail -n 100 laravel/storage/logs/stripe-sync.log

# Send one donation's receipt, by its Stripe payment ID, such as one synced
# too late to be receipted automatically
sudo -u deploy docker compose exec app php artisan receipt:send pi_...

# List failed queued jobs, then retry one by its ID, or all of them
sudo -u deploy docker compose exec app php artisan queue:failed
sudo -u deploy docker compose exec app php artisan queue:retry <id>
sudo -u deploy docker compose exec app php artisan queue:retry all

# Git commands run as the clone's owner. Git refuses to run as root in a clone
# owned by another user ("dubious ownership"), which also keeps root from
# creating files in the clone that the containers cannot write.
sudo -u deploy git status
```

### Launching Donations

Donations need these steps once per server, after the code that includes them has deployed. Staging uses its own Stripe sandbox and production the live account; the two never share keys, products, or webhook endpoints.

**Server settings**

1. In `laravel/.env`, switch the framework drivers to the database: `CACHE_STORE=database` and `QUEUE_CONNECTION=database`. Without this, webhooks are stored but nothing processes them.

**Stripe (the server's sandbox or live account)**

2. **Payment methods:** turn off Klarna, whose [rules](https://docs.stripe.com/payments/klarna/compliance) don't allow charities. Before enabling any other buy now, pay later method, check its rules the same way.
3. **Default API version:** upgrade it to our pinned version (`services.stripe.api_version`), in Settings → Developers → Preferences.
4. **Donation product:** one product (Product catalog → Add product). Its name and image appear on the payment page; it needs no price of its own.
5. **Customer Portal** (Settings → Billing → Customer portal): activate the login link; allow payment method updates and immediate cancellation; turn off plan switching and customer information updates; turn on invoice history; and set the default redirect link to the site.
6. **Customer emails** (Settings → Emails): turn off Stripe's receipts for successful payments, since the site sends its own donation receipts. Keep Stripe's emails about failed payments and expiring cards, which the site doesn't send.
7. **Branding and public details** (live account): logo, colors, business name, and support email, shown on Checkout and the portal.
8. **Restricted key:** create one with only the permissions the site uses: Checkout Sessions (write), Customers (write), Products, Payment Intents, Charges and Refunds, Balance, Subscriptions, and Invoices (read). Not Debugging Tools, which only the local Stripe CLI needs. Check its request logs (⋯ → View request logs) after the first donations, and remove anything it never used.
9. **Webhook endpoint:** register it as described under [Stripe](#stripe), at `https://<host>/webhooks/stripe`.

**Server settings again**

10. **Email:** set the server's AhaSend SMTP credential and the `MAIL_*` settings in `laravel/.env` (see [Email](#email)), unless setup already did. Production needs a live credential.
11. Set `STRIPE_SECRET`, `STRIPE_WEBHOOK_SECRET`, `STRIPE_DONATION_PRODUCT_ID`, and `STRIPE_PORTAL_LOGIN_URL` in `laravel/.env`, then deploy by hand (`sudo systemctl start wildland-deploy`). The deploy's `stripe:check` fails if a key is for the wrong mode or a setting is missing.
12. Check email after that deploy: `sudo -u deploy docker compose exec app php artisan mail:test <your address>`. With a live credential, the email should arrive.
13. Import past history, including Payment Link donations: `sudo -u deploy docker compose exec app php artisan stripe:sync`.
14. Make a donation (a test card on staging, a small real one on production), and check that it reaches the `donations` table and the endpoint's Event deliveries show `200`s.

**Production, after launch**

15. Archive the old Payment Link products once the donate page has replaced the Payment Links.

### Switching Branches

A server deploys the branch named by `DEPLOY_BRANCH` in its root `.env`, so it can run another branch (for example, to try a feature branch on staging) without changing anything in GitHub. From the clone's directory, with the branch already pushed:

```bash
# Point the server at the branch
sudo -u deploy sed -i 's/^DEPLOY_BRANCH=.*/DEPLOY_BRANCH=feature-branch/' .env

# Deploy it now, and follow the output
sudo systemctl start wildland-deploy
journalctl -u wildland-deploy -f
```

The deploy checks out the new branch and recreates the webhook container with the new `DEPLOY_BRANCH`, so from then on pushes to that branch deploy automatically and pushes to the old branch are ignored. The GitHub webhook already sends every push, so it needs no changes.

Switch back the same way, with `main` on staging or `release` on production.

Migrations are not rolled back when switching. If the branch adds migrations, run `sudo -u deploy docker compose exec app php artisan migrate:rollback --step=<count>` before switching back, so the database matches the original branch again.

### Domains

| Domain | Server | Serves |
|--------|--------|--------|
| `stage.wildland.eco` | Staging | The site, with a `noindex` header; webhook at `/hooks/deploy` |
| `wildland.eco` | Production | The site |
| `www.wildland.eco` | Production | Permanent redirect to `https://wildland.eco` |
| `prod.wildland.eco` | Production | The server's own hostname: the site with a `noindex` header, and the webhook at `/hooks/deploy` |

Each domain needs a DNS record pointing at its server before Caddy can obtain its certificate. The webhook uses `prod.wildland.eco` so the server can be tested and reached directly, whatever `wildland.eco` points at. To move production to a new server, set it up with `prod.wildland.eco` pointing at it, check the site there, then point `wildland.eco` and `www.wildland.eco` at it; Caddy obtains their certificates on the first requests after DNS changes.

The `noindex` header (`X-Robots-Tag`) keeps search engines from listing staging and the production hostname. A `robots.txt` `Disallow` is not used, because crawlers that are blocked from a page never see its `noindex` header.

# Deployment

## Local Development

### Laravel (Docker)

The Docker environment was generated by [Wetfish Skeleton](https://github.com/wetfish/skeleton). The same `docker-compose.yml` runs locally, on staging, and in production:

| Service | Image | Purpose |
|---------|-------|---------|
| app | php:8.5-fpm (custom `Dockerfile`) | PHP-FPM with Laravel extensions and Composer |
| nginx | nginx:alpine | Serves `laravel/public/`, proxies PHP to app |
| db | postgis/postgis:17-3.5 | PostgreSQL 17 + PostGIS 3.5 |
| node | node:24-slim | Builds frontend assets; runs on demand with `docker compose run --rm node`, never as a long-running container |

Published ports are bound to `127.0.0.1`, so the site and database are reachable only from the machine itself. On servers, a reverse proxy handles public traffic.

Configuration is split across two gitignored files:

- **Root `.env`:** Docker settings (container name prefix, ports, user and group IDs, database credentials, and on servers the deploy branch). Copy from `.env.example`.
- **`laravel/.env`:** Laravel settings. Copy from `laravel/.env.example`. `DB_PASSWORD` must match the root `.env`.

First-time setup from a fresh clone:

```bash
cp .env.example .env
cp laravel/.env.example laravel/.env
docker compose up -d
docker compose exec app composer install
docker compose exec app php artisan key:generate
docker compose exec app php artisan migrate
docker compose run --rm node npm ci
docker compose run --rm node npm run build
```

Set a real `DB_PASSWORD` in both `.env` files before the first `docker compose up`, because PostgreSQL stores the password when the database volume is created. The site is served at `http://localhost:8080` (or the `NGINX_PORT` in the root `.env`).

Set `UID` and `GID` in the root `.env` to your user's IDs (`id -u` and `id -g`) so files created by the containers stay editable.

Rebuild assets with `docker compose run --rm node npm run build` after changing styles or scripts. For hot reloading, run `npm run dev` in `laravel/` with Node installed on the host; running the Vite dev server in Docker is not set up yet.

## Servers

Staging (`stage.wildland.eco`) and production (`prod.wildland.eco`, and `wildland.eco` after cutover) each run on their own server from a clone of the repository, using the same `docker-compose.yml` as local development. The clone can be in any directory; deploys run as the user who owns it. Two more services run only on servers, enabled by `COMPOSE_PROFILES=server`:

| Service | Purpose |
|---------|---------|
| caddy | Terminates HTTPS on ports 80 and 443, obtains and renews certificates automatically, and forwards requests to nginx. Configured by `deploy/caddy/<CADDY_SITE>.Caddyfile`. |
| webhook | Receives GitHub push webhooks at `/hooks/deploy`. It verifies the signature and branch, then writes `deploy/trigger/deploy-requested`. It has no Docker access, and its port (9000) is reachable only by Caddy over Docker's internal network. |

### How Deploys Work

1. A push to the server's branch sends a webhook to `https://<server domain>/hooks/deploy`. Caddy receives it on the standard HTTPS port and forwards it to the webhook container; no other port needs to be opened.
2. The webhook container checks the `X-Hub-Signature-256` signature against `WEBHOOK_SECRET` and that the push is to `refs/heads/<DEPLOY_BRANCH>`. Anything else gets a 403.
3. A verified push writes the trigger file. The `wildland-deploy.path` systemd unit on the host sees the change and starts `wildland-deploy.service`, which runs `deploy/deploy.sh` as the clone's owner.
4. `deploy/deploy.sh` checks out the branch's latest commit, rebuilds and restarts containers, reloads the Caddy config, installs PHP dependencies without dev packages, builds assets, runs migrations, and caches configuration, routes, and views. If more commits arrived during the deploy, it deploys again.

Deploys in the same environment never overlap. The clone is used only for deploys: the script discards local changes to tracked files, while untracked files such as `.env` and `laravel/.env` are kept. To move a server to another branch, change `DEPLOY_BRANCH` in its root `.env`; the next deploy checks that branch out.

### Server Settings

| File | Setting | Staging | Production |
|------|---------|---------|------------|
| Root `.env` | `COMPOSE_PROFILES` | `server` | `server` |
| Root `.env` | `CADDY_SITE` | `staging` | `production` |
| Root `.env` | `DEPLOY_BRANCH` | `main` | `release` |
| Root `.env` | `WEBHOOK_SECRET` | Random, unique per server | Random, unique per server |
| `laravel/.env` | `APP_ENV` | `production` | `production` |
| `laravel/.env` | `APP_DEBUG` | `false` | `false` |
| `laravel/.env` | `APP_URL` | `https://stage.wildland.eco` | `https://prod.wildland.eco`, then `https://wildland.eco` |

Staging uses `APP_ENV=production` so it behaves exactly like production. Each server gets its own `APP_KEY`, database password, and webhook secret.

### Setting Up a Server

`deploy/setup.sh` sets up a server in one run, from a clone of the repository. It needs a Debian or Ubuntu server with sudo access, and the server's domain (`stage.wildland.eco` or `prod.wildland.eco`) already pointing at it so Caddy can obtain the HTTPS certificate.

Clone the repository into any directory, then run the script:

```bash
sudo apt install git
git clone https://github.com/Wildland-Ecotech/wildland.eco.git
cd wildland.eco
sudo deploy/setup.sh
```

Until `laravel-integration` is merged, `main` does not contain the setup script yet: run `git checkout laravel-integration` before `sudo deploy/setup.sh`, and answer `laravel-integration` when the script asks which branch to deploy.

The script asks for:

- **Environment:** `staging` or `production`
- **Branch to deploy:** defaults to `main` for staging and `release` for production. If the branch does not exist on GitHub yet, or does not contain the Laravel site, the script says so and asks again.
- **AhaSend SMTP username and password:** optional; without them, email is written to the Laravel log

It then:

1. Makes sure the clone has a non-root owner. Deploys and containers run as the clone's owner, and the containers must not run as root: PHP-FPM started as root serves requests as `www-data`, which cannot write to root-owned storage. If the clone is owned by root (for example, cloned into `/opt` as root), the script creates a `deploy` user with no password or login shell and gives it the clone.
2. Installs Docker Engine with the Compose plugin from Docker's apt repository.
3. Adds the clone's owner to the `docker` group, since deploys run as that user. Membership in the `docker` group is equivalent to root access.
4. Writes both `.env` files from their examples with the server settings, generating the database password, `APP_KEY`, and webhook secret. Both files are readable only by the clone's owner.
5. Runs the first deploy, which builds the containers, obtains the HTTPS certificate, and sets up the database.
6. Installs the systemd units that run deploys when the webhook fires, with the clone's path and owner filled in. They are copied rather than linked, so a deploy can never change the host's services.
7. Prints the settings for the GitHub webhook.

The one manual step is adding the webhook in GitHub (repository Settings → Webhooks → Add webhook) with the printed payload URL, content type, and secret, for push events only. GitHub's first test ping gets a 403 response, because only pushes to the server's branch start a deploy.

The script is safe to re-run. It keeps existing `.env` files (updating only the container user IDs if the clone's owner changed) and repeats the remaining steps, so re-running it after the systemd units change in the repository installs the new versions.

### Operating a Server

```bash
# Deploy the latest commit by hand
sudo systemctl start wildland-deploy

# Follow deploy output
journalctl -u wildland-deploy -f

# Webhook and Caddy logs (from the clone's directory)
docker compose logs -f webhook caddy

# Git commands in a clone owned by the deploy user
sudo -u deploy git status
```

## Production

### Current Hosting

Until the Laravel site is deployed (milestone 4), wildland.eco is the static SvelteKit build from the `ui/` directory on the `main` branch (`ui/public_html/`), served by nginx on an existing server behind HTTPS managed by Certbot. The `laravel-integration` branch no longer contains `ui/`. nginx must include `try_files $uri $uri.html $uri/ =404;` to serve SvelteKit's generated pages without `.html` extensions:

```nginx
server {
    server_name wildland.eco *.wildland.eco;
    root /home/sites/wildland.eco/ui/public_html;

    location ~ /\. {
        deny all;
        return 404;
    }

    location / {
        index index.html;
        try_files $uri $uri.html $uri/ =404;
    }
}
```

The repository previously included a GitHub Actions workflow to publish Docker images to GHCR for Watchtower to deploy. It never succeeded and has been removed.

### Cutover

The steps for moving wildland.eco from the old server to the production server without downtime are in [milestone 4](06-planned-features.md#4-production-server-and-deploys).

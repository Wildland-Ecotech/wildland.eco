## Form Submissions

Both forms' POST routes (`POST /donate` and `POST /leaves/apply`) record every submission in `form_submissions` the moment it arrives, with the `RecordFormSubmission` middleware (`app/Http/Middleware/RecordFormSubmission.php`, added as `RecordFormSubmission:donation` and `RecordFormSubmission:leaf_application`). Nothing a visitor typed is lost, even when something fails:

1. **Arrival.** The middleware runs right after the session starts and before the CSRF check (its place is set in `bootstrap/app.php` with `appendToPriorityList()`), so even a submission from a page that had expired is recorded. It saves the reference, name, email, the other fields, and the browser, with the outcome `received`, and keeps the submission on the request for the controller (`FormSubmission::forRequest()`).
2. **Outcome.** Controllers record what happened with `markAs()`: `unavailable`, `rate_limited`, `payment_error`, `sent_to_payment` (with the checkout), or `saved` (with the application). Anything else is worked out from the response when the request ends: a 419 is `expired`, a 5xx is `error`, and errors flashed to the session are `rejected`. The messages the visitor was shown are saved with it.
3. **Failures.** For a failed submission, the middleware writes a warning to the Laravel log with the reference, form, outcome, and the names of the fields that failed, never what was typed, and flashes the reference to the session. Both forms show it under their errors, asking the visitor to include it if they email us.

`php artisan submissions:list` lists the submissions that need a follow-up (see [submissions:list](02-services-and-commands.md#submissionslist-appconsolecommandslistformsubmissionsphp)).

## Stale Forms

A form's CSRF token stops working when its session expires (`SESSION_LIFETIME`, 120 minutes), and its proof-of-work challenge expires after two hours (`ProofOfWork::LIFETIME`). A visitor coming back to a form left open would otherwise get a "page expired" error or a proof-of-work error. Both forms carry `data-form-tokens-url`, and `resources/js/proof-of-work.js` fetches fresh tokens from `GET /form-tokens`:

1. **Before submitting**, if the page was loaded (or last refreshed) more than 30 minutes ago, it replaces the form's `_token` and challenge, solves the new challenge, then submits. A newer page submits right away.
2. **When the visitor comes back** to the tab (it becomes visible or focused) after 30 minutes, it refreshes them ahead of time, so the submit doesn't wait.
3. If the request fails, the form is sent with its current tokens, and the server explains any problem (the branded "page expired" page, or the proof-of-work message).

If the session had expired, fetching the token starts a new one, so the refreshed token matches the cookie the response sets. Only the site's own pages can read the response, so it gives other sites no way to get a token.

## Donations

Payment happens on the payment gateway's hosted page (Stripe Checkout); payments are recorded from the gateway's webhooks, not by these routes. See [Donation Flow](06-planned-features.md#donation-flow).

1. `GET /donate` shows the form with a new proof-of-work challenge. While the gateway is not configured (`PaymentGateway::isAvailable()`, false without `STRIPE_SECRET`), the page says online giving is unavailable and the button is disabled.
2. `POST /donate` is validated by `StartDonationRequest`:
   - The amount is the custom amount when one is entered, otherwise the suggested amount for the chosen frequency, from that frequency's own field (`amount_one_time`, `amount_monthly`, `amount_annual`). The custom amount is cleaned first (spaces, `$`, and commas removed), so `$1,250.50` is accepted.
   - It must be $1 to $9,999 (`MIN_AMOUNT`, `MAX_AMOUNT`) with at most two decimal places, and is converted to cents exactly from the string (`amountCents()`).
   - The frequency must be `one_time`, `monthly`, or `annual`; name and email are required; and the proof of work is checked as on the leaf form.
   - Failures redirect back with errors and the visitor's input. Like every outcome, they are recorded in `form_submissions` (see [Form Submissions](#form-submissions)).
3. The controller refuses if the gateway became unavailable, and allows `DonationController::MAX_PER_HOUR` (10) started checkouts per IP address per hour. Only checkouts that reach the gateway count.
4. In one transaction, it finds the user by email, including a soft-deleted one, or creates them with the name entered. An existing user's name is only filled in when it is empty: typing an email address proves nothing about owning it. A soft-deleted user is not restored here. It then records a `started` checkout for the General Fund.
5. `PaymentGateway::startCheckout()` creates the gateway session, with the thank-you URL as the success URL and `/donate` as the cancel URL. The checkout's `gateway_session_id` and `expires_at` are saved, and the donor is redirected to the gateway. If the gateway call fails, the error is reported, the donor is sent back with a message and their input, and the checkout stays recorded without a session.
6. `GET /donate/thank-you/{reference}` finds the checkout by its UUID reference; anything else is a 404. It shows the donation's amount and frequency, never the donor's name or email, and for recurring donations a link to the Customer Portal login (`STRIPE_PORTAL_LOGIN_URL`).

## Stripe Webhooks

Stripe sends events to `POST /webhooks/stripe`: from each server's registered webhook endpoint, or locally from the Stripe CLI. Responses follow [Webhook Responses](05-ai-development-notes.md#webhook-responses): errors only when something is actually wrong, because Stripe retries failed deliveries for days.

1. **Signing secret.** If `STRIPE_WEBHOOK_SECRET` is not set, the request fails with a 500 and an error is logged.
2. **Signature.** The `Stripe-Signature` header is verified against the raw request body with the Stripe SDK (`Webhook::constructEvent()`), which also rejects signatures more than 5 minutes old, so a captured event can't be replayed. A missing or invalid signature is a 400. The route skips CSRF protection, since Stripe can't send a token, and skips sessions and cookies, since there is no visitor.
3. **Mode.** An event from the other Stripe mode (its `livemode`, see [StripeMode](02-services-and-commands.md#stripemode-apppaymentsstripestripemodephp)) is a 400 and is logged as an error.
4. **API version.** An event whose `api_version` differs from `services.stripe.api_version` is accepted, with a warning in the log (see [Updating the Stripe API version](07-deployment.md#updating-the-stripe-api-version)).
5. **Storage.** The event is stored in `webhook_events` once per event ID; a redelivery finds the stored row. Every event Stripe sends is stored, including types we don't handle.
6. **Queue.** If the event hasn't been processed yet, `ProcessWebhookEvent` is queued and the response is `200 Queued`; if it has, `200 Already processed`. Processing happens on the queue worker (see [ProcessWebhookEvent](02-services-and-commands.md#processwebhookevent-appjobsprocesswebhookeventphp)).

## Leaf Applications

1. `GET /leaves/apply` shows the form. The controller passes `earliestReadyDate` (tomorrow in Fort Collins) for the date field's `min`, and a new proof-of-work challenge (see [ProofOfWork](02-services-and-commands.md#proofofwork-appservicesproofofworkphp)).
2. `POST /leaves/apply` is validated by `StoreLeafApplicationRequest`:
   - The bag count is cleaned first (spaces and commas removed), so `1,200` is accepted.
   - `phone` must be a US number with its area code: 10 digits, or 11 starting with a country code 1 or +1, typed with any spaces, dots, dashes, or parentheses, and optionally an extension after it ("x", "ext", "ext.", or "extension", then up to 6 digits), such as `(970) 555-0123` or `970-555-0123 x12` (`ContactDetail::PHONE_PATTERN`). The admin contact forms take phone numbers by the same rule, with the same message: "Enter a phone number with its area code, such as (970) 555-0123, and any extension after it, such as x12." Numbers saved before the rule, such as one without an area code, are kept as they were.
   - `ready_date` is required only when `ready_now` is `0`, and must be after today in `America/Denver` (`StoreLeafApplicationRequest::TIMEZONE`), not the server's UTC date.
   - `terms` must be accepted.
   - `pow_challenge` and `pow_nonce` must be a solved, unexpired, unused proof of work, checked in the request's `after()` hook. A checked challenge is used up even when other fields fail, and the redisplayed form issues a new one.
   - Failures redirect back with errors and the visitor's input.
3. The controller allows `LeafApplicationController::MAX_PER_HOUR` (5) saved applications per IP address per hour. Only saved applications count, so validation errors never lock anyone out.
4. The application is saved, with `ready_date` cleared when the bags are ready now and `terms_accepted_at` set to the current time, then linked to its contact by [ContactLinker](02-services-and-commands.md#contactlinker-appservicescontactlinkerphp); a failure linking is reported and never shown to the visitor. The visitor is redirected to `GET /leaves/apply` with `applied` (the application type) flashed to the session, which shows the thank-you message.

## Signing In

Admins sign in with their email address and password at `/login`, using Laravel's built-in session authentication (`Auth::attempt()`) rather than an authentication package. Admins are created, and their passwords set, with [users:admin](02-services-and-commands.md#usersadmin-appconsolecommandsmanageadminphp); there is no registration or password reset page yet. The same sign-in page will serve donors once donor accounts are built (see [Accounts](06-planned-features.md#accounts)).

1. `POST /login` is validated by `LoginRequest`: the email address is trimmed and lowercased, since addresses are stored lowercase, and both fields are required. So is a proof of work, as on the leaf application form ([ProofOfWork](02-services-and-commands.md#proofofwork-appservicesproofofworkphp)), which makes guessing passwords by script expensive: without JavaScript, the page says signing in needs it, and a missing or reused proof is refused with "We could not verify your browser. Reload the page and try again with JavaScript turned on."
2. `LoginController` allows `MAX_ATTEMPTS_PER_MINUTE` (5) failed attempts per email address and IP address per minute, and `MAX_ATTEMPTS_PER_IP_PER_HOUR` (20) per IP address per hour across every email address, so one address can't try account after account. After either, even the right password is refused with a message to wait a minute, or an hour. A successful sign-in clears the per-address count, not the IP address's.
3. Only users with the `admin` role can sign in until donor accounts are built, and soft-deleted users never can. A wrong password, an unknown email address, and a donor's account all get the same message, so the form can't be used to find out who has an account.
4. Failures redirect back with the email address only, never the password. The sign-in form isn't recorded in `form_submissions`, which is for following up with visitors; instead `RecordLoginAttempt`, on `POST /login`, records every attempt in [login_attempts](01-database-schema.md#login_attempts): the email address, the admin account it belongs to, the IP address, the browser, and the outcome, never the password. Like `RecordFormSubmission`, it runs right after the session starts, before the CSRF check, so an attempt from an expired page is recorded too. The controller says what happened with `LoginAttempt::outcomeFor()`, which works from the form request because the attempt is the same object on its copy of the request's attributes.
5. A successful sign-in gets a new session ID, then goes to the admin page the admin first asked for, or `/admin`. There is no "remember me": a session lasts `SESSION_LIFETIME` (120 minutes) after the last request.

**Sign-Ins (`/admin/sign-ins`)** lists the recorded attempts newest first, up to `SignInReport::LIST_LIMIT` (500; the summary says "The newest 500 of 1,234 sign-in attempts." when there are more): when, the email address as typed, the outcome (`LoginAttempt::label()`: Signed in, Wrong password for an admin's address, No admin account for any other, Too many attempts, No proof of work, Missing email or password, Page expired, or Error), the IP address, linking to every attempt from it, and the browser, roughly, from its user agent (`LoginAttempt::browser()`, such as "Firefox on Linux"; anything else, such as `curl/8.5.0` or a headless browser, as it is). `show=failed` lists only those that didn't sign anyone in, and `q` those whose email or IP address contains it. It's opened from the Sign-Ins button on Error Logs, which the menu shows as current, so it has no link of its own. While any attempt failed in the last 24 hours, the dashboard and Error Logs show a red warning (`SignInReport::notice()`), such as "5 failed sign-in attempts in the last day, 3 from 203.0.113.77.", with a Review Sign-Ins button to the failed ones; Sign-Ins shows it without the button.

Admin pages use three middleware:

- **`auth`** sends guests to `/login`, and back to the page they asked for afterwards.
- **`auth.session`** (Laravel's `AuthenticateSession`) signs out every other session when an admin's password changes, such as after `users:admin` sets a new one.
- **`AdminOnly`** (`app/Http/Middleware/AdminOnly.php`) refuses anyone without the `admin` role with a 403, checked on every request so `users:admin --remove` takes effect right away. Responses are sent with `Cache-Control: no-store, private` and `X-Robots-Tag: noindex, nofollow`, since admin pages show donors' personal details.

Sessions are stored in the `sessions` table (`SESSION_DRIVER=database`), and servers set `SESSION_SECURE_COOKIE=true` so the session cookie is only sent over HTTPS (see [Server Settings](07-deployment.md#server-settings)).

## Admin Pages

Admin pages show the same records and values as the report commands, from the report classes and describing traits in `app/Reports/` (see [Report Classes](02-services-and-commands.md#report-classes-appreports)), so a page and its command can't disagree. Controllers for admin pages live in `app/Http/Controllers/Admin/`, and every route is under `/admin` behind the middleware in [Signing In](#signing-in).

**Dashboard (`/admin`)** shows who is signed in, then a red warning while contacts are waiting to hear from us or have bags ready and haven't heard from us yet, counted as Contacts labels them ("3 people are waiting to hear from us, and 2 more have bags ready."; `App\Reports\FollowUpNotice`), with a Follow Up button to Contacts. There's no warning when there are none, and no other page shows it, since Follow Up opens Contacts. Another warns while attempts to sign in failed in the last day, as on Error Logs (see [Signing In](#signing-in)). Then **Recent Activity**: four counts for the last 90 days (`DashboardController::DAYS`), donations received, leaf applications, unresolved errors (leaving out errors the visitor got through later, and those an admin closed), and applications to review (applications from those days whose contact still needs an admin to look). Each comes from the same report class or query as its list, so it matches that list with the Last 90 days period, and links to it; unresolved errors link to Error Logs with `later=0&resolved=0`, and applications to review to Needs Review, which lists every one, however old. Then **Donation Statistics**: what `donations:totals` shows, one list each for month over month, by quarter, by year, and all time, with the same notice when Stripe's fee isn't recorded yet for some donations. `/admin/donations/totals/csv` (`DonationTotalsController`) downloads `donation-totals-<date>.csv` with the same columns as `donations:totals --csv`. The totals had a page of their own, `/admin/donations/totals`, which now redirects to the dashboard.

**Contacts (`/admin/contacts`)** lists every contact from `ContactReport`, as an overview: whether their latest application is for a pickup or drop-off, the bags on their pending applications and the bags they've given (from logged pickups and drop-offs), their number of applications, and when they last applied, with drop-off sites labeled. Phone numbers and emails are on each contact's page. Each contact with a pending application has their group (Waiting on us, Ready, Contacted, or Later) and why, such as "No word from us in 10 days", "Their text on Nov 5 needs a reply", "Follow-up due today", "Follow up on Nov 13", "Bags ready Dec 5", or "Reached Nov 2", for their first application in the follow-up order from `FollowUpReport` (see [Report Classes](02-services-and-commands.md#report-classes-appreports)). Applications not linked to a contact are left to Needs Review. By default (`sort=follow-up`) those who need follow-up come first, in the follow-up order, then everyone else, the person who applied most recently first and contacts without an application last; with `sort=recent`, everyone is in that order. `q` searches part of a name or email, or part of a phone number's digits however it was written, including previous ones (up to `ContactController::MAX_SEARCH_LENGTH`, 100 characters). It's a plain `GET` form, so a search is a URL. `/admin/contacts/{contact}` shows one contact's details, their address linking to the Map with them and the drop-off sites (`/admin/map?contact={id}`), with their follow-up group and why when they have a pending application, the other contacts sharing a phone number or email, their timeline, their applications with each one's status, and their form submissions that didn't go through, with how each was followed up (`FormSubmissionReport::forContact()`). The timeline, newest first, holds their logged entries ([contact_activities](01-database-schema.md#contact_activities)) and, added automatically, their applications and form submissions that didn't go through. A contact merged into another redirects to that one with "That contact was merged into Jamie Rivera."; an unknown contact, or one deleted without merging, is a 404. Contacts have no report command, and no CSV download yet.

**Needs Review (`/admin/contacts/review`)** lists the applications whose contact needs an admin to look (`LeafApplication::needingContactReview()`: flagged and not reviewed yet; see [leaf_applications](01-database-schema.md#leaf_applications)), oldest first, however old: ID (the link to the application), when applied, name, the contact it's linked to (linking to them) or "Not linked", and why. The contact list shows a Needs Review button with the count, only while there are any, and the dashboard counts those from the last 90 days.

**Adding a contact** (`/admin/contacts/new`), such as someone reached by text before they applied, takes a name, and optionally a phone number, email, address, and notes, and whether it's one of our drop-off sites (`is_drop_off_site`; `SaveContactRequest`). When another contact, not deleted, already has the phone number or email, current or previous, nothing is added: the form comes back with its input and a notice for each, such as "970-555-0123 is already Jamie Rivera's phone number." (formatted, however it was typed) (or "was", for a previous one), linking to that contact, and a box to "Add as a separate contact anyway" (`separate`). A contact added this way gets linked to the applications they send later, like any contact with the same name and phone number or email (see [ContactLinker](02-services-and-commands.md#contactlinker-appservicescontactlinkerphp)). It goes to the new contact's page with "Added Pat Morgan."

**Logging activity** (`/admin/contacts/{contact}/activities/new`, from the Log Activity button under a contact's Timeline): what happened (`type`: text, call, visit, note, pickup, or drop-off), who reached out (`direction`, required for texts and calls), when (`happened_at`, a Fort Collins date and time, now by default, never in the future), what was said or the note (`body`, optional, up to 5,000 characters), bags (`bag_count`, required for pickups and drop-offs; commas and spaces are stripped), the application (`leaf_application_id`, one of the contact's pending applications, newest first and chosen by default, or None), and a follow-up date (`follow_up_on`, today or later), validated by `LogContactActivityRequest`. The application and follow-up fields show only when the contact has a pending application. The server keeps the direction only for texts and calls, and bags only for pickups and drop-offs; `_admin.scss` hides those fields for other kinds with `:has()`. It records which admin logged it. A pickup or drop-off for an application marks it complete. A follow-up date goes on the application chosen, or on all their pending applications when None is chosen. Save goes back to the contact with "Logged a pickup of 28 bags."; Save and Add Another (`add_another`) comes back to the form with the same kind, direction, and application, for the reply in a back-and-forth. A deleted contact is a 404.

**Merging contacts:** a contact's page lists the other contacts, not deleted, that have one of its current phone numbers or emails as a current one of theirs (`ContactReport::sharing()`); a previous number or email on either side doesn't count, so changing a number settles it, each with a Merge Into button. It posts to `/admin/contacts/{contact}/merge/{other}`, which merges the other contact into this one ([ContactMerger](02-services-and-commands.md#contactmerger-appservicescontactmergerphp)) and goes back with "Merged Jamie R. into Jamie Rivera, with 1 application." There's no confirmation step, since the merged contact is only soft-deleted. Merging a contact into itself, or with a deleted one, is a 404.

**Editing a contact** (`/admin/contacts/{contact}/edit`): the name, notes, and drop-off site box are saved together. The box sends `0` from a hidden field when unchecked. Each phone number, email, and the address is its own small form (`ContactDetailController`): adding one (`AddContactDetailRequest`, a hidden `type` and a field named after it, so an error shows by the right box; it becomes the main one only when there's none yet, and one already on the contact changes nothing), Make Main, and Remove. Changing the address keeps the previous one, and Remove keeps a detail as a previous one, so applications still match it. Each goes back to the edit page with a message. A detail in the URL must be the contact's own, so another contact's is a 404 (`scopeBindings()`), as is a deleted contact. Edits aren't recorded yet; the record of edits comes after launch.

**Deleting a contact:** a contact no application belongs to, even a deleted one, such as one added by mistake or as a test, can be deleted from the end of their edit page, as can contacts with only test and spam applications (see [leaf_applications](01-database-schema.md#leaf_applications)). It posts to `/admin/contacts/{contact}/delete` with a checked `confirm` box (`DeleteContactRequest`, which also refuses contacts with real applications, in case one was linked since the page opened; an error goes back to the edit page's Delete Contact section, `#delete`). The contact is only soft-deleted, like a merged one, with their details and timeline kept, and the page goes to Contacts with "Deleted Pat Morgan." A contact with a real application can't be deleted; a duplicate is merged instead.

**Donations (`/admin/donations`)** lists payments like `donations:list`. Its filters are a plain `GET` form, so a filtered list is a URL that can be bookmarked or shared with another admin:

| Query | Values | Default | Like |
|-------|--------|---------|------|
| `period` | `30`, `90`, `365`, or `all` (`FiltersByPeriod::PERIODS`, shared by admin lists) | `30` | `--days` |
| `type[]` | `one-time`, `monthly`, `annual`, any combination; none lists every type | none | `--one-time`, `--monthly`, `--annual` |
| `all` | `1` includes pending and failed payments | received only | `--all` |

Anything else, such as a hand-edited URL, falls back to the defaults, since the form can only send these values. `/admin/donations/csv` takes the same query and downloads `donations-<date>.csv` with the same columns as `donations:list --csv`, including the protection against spreadsheet formulas. `/admin/donations/{donation}` shows what `donations:view` shows, with the same notices for a fee not recorded yet and a deleted donation; an unknown ID is a 404.

**Abandoned Checkouts (`/admin/donations/abandoned`)**, reached from the Abandoned Checkouts button on Donations, lists checkouts like `donations:abandoned`, with the same `period` filter as the other lists, and says how many donors donated later. Checkouts have no page of their own, so the list has no links. `/admin/donations/abandoned/csv` takes the same query and downloads `abandoned-checkouts-<date>.csv` with the same columns as `donations:abandoned --csv`, including the donors' names and email addresses.

**Map (`/admin/map`)**, after Contacts in the navigation, is for planning pickups and finding the closest drop-off site (`MapReport`). Locations come from contacts' current addresses (`ContactDetail::location`), so an application is on the map once its contact's address is located.

**Trailer Loads** comes first on every view but an opened load, before the map, so the planned loads are what's seen on arrival: date (opening the load), stops, and bags against the capacity, soonest first, or "No trailer loads are planned."; then done and canceled loads, newest first, folded under "Past loads (4)" (a `<details>`, which opens without JavaScript), with their status.

- **Needs scheduling** (`show=pickups`, the default): pending pickups not in a planned trailer load whose contact's address has a location, colored by when the bags are ready (red: ready now, overdue, or within 7 days; yellow: within 14; green: later), and the drop-off sites in gray. Under the map, each of those pickups soonest first, with a running total of bags for filling the trailer, marking those not on the map yet. The summary says how many more are in a planned load.
- **A new trailer load** (`build=1`, from Start a Trailer Load on Needs scheduling): a form with the day it's planned for (today to start), the trailer's capacity in bags (80 to start), and a progress bar, then Save Load and Cancel. Each pickup in the list gets a box belonging to the form (`stops[]`, the application's ID); with JavaScript, clicking a pickup's dot checks or unchecks it, the chosen dots are numbered in the order they were clicked, the form sends the stops in that order, and the bar follows the chosen bags (from `#load-bags`). Without JavaScript, the stops are sent in the list's order. `POST /admin/map/loads` (`SaveTrailerLoadRequest`) takes the date, the capacity as typed (commas and spaces removed, 1 to 1,000), and the stops once each, in order; every stop must be a pending pickup not already in a planned load, or the form comes back saying so with the boxes still checked and numbered in the order chosen (`#load-order`). A load can be over its capacity. It saves the load and its stops (`TrailerLoadController`) and opens it with "Saved the Sun, Nov 8 load: 3 stops, 70 bags."
- **A trailer load** (`load`, its ID; an unknown one is a 404), to follow on a phone while signed in: headed "Trailer Load: Sun, Nov 8", with its status and stops, the progress bar, its stops on the map numbered in route order with the drop-off sites, and **Stops**: stop number, name (linking to the contact), bags, address, main phone number (a `tel:` link, `+1` and its 10 digits, so a tap dials it), and the contact's notes, which can hold things like a gate code. It has no filters, Trailer Loads list, or Locate Addresses, and "← Back to Map" goes back. Loads aren't printed. A planned load also has:
    - **Edit Load** (`edit=1`): the New Trailer Load form as "Edit Load", filled with the load's date and capacity, its pending stops checked, and the map numbering them in route order (`#load-order`), with the pickups not in another load to add, numbered after the load's stops in the order clicked. `POST /admin/map/loads/{load}` validates it like a new load, letting the load keep its own stops, and saves it (`TrailerLoadController@update`): stops still chosen keep their order, new ones go at the end, and those taken out are deleted from the load and need scheduling again. A stop no longer pending, such as one whose pickup was logged on its own, stays. It goes back to the load with "Saved the Sun, Nov 8 load: 4 stops, 95 bags."
    - **Up** and **Down** on each stop (none past either end), each a small form posting to `/admin/map/loads/{load}/stops/{application}/up` or `down`, which swaps it with its neighbor, numbers the stops from 1 again, and goes back to `#stops`. A stop not in the load is a 404.
    - **Mark Done** (`/admin/map/loads/{load}/done`), beside Edit Load, once the load has been picked up: "Mark Load Done", with When (now, in Fort Collins time) and each stop still pending in route order, checked, with its bags filled in from the application ("estimated 25") to correct. A stop not linked to a contact has no box, since a pickup goes on a contact's timeline; it says to link it and log the pickup from the contact's page. `POST /admin/map/loads/{load}/done` (`MarkTrailerLoadDoneRequest`) takes `finished_at` (not in the future), `stops[]`, and `bags[ID]` (commas and spaces removed, 1 to 10,000) for each stop checked; an unchecked stop's bags are ignored, and a stop that can't be logged anymore (`TrailerLoad::loggableApplications()`: pending, not deleted, linked to a contact) sends the form back with "A stop changed since this page opened." It logs a pickup on each checked stop's contact (`ContactActivity`, by the admin), which marks the application complete, keeps it on the stop (`contact_activity_id`), and marks the load done, recording when and by whom (`TrailerLoadController@finish`). Unchecked stops stay pending and need scheduling again. It goes back to the load with "Logged 2 pickups, 38 bags, and marked the Sun, Nov 8 load done. 1 stop needs scheduling again." A load can be marked done with nothing checked. A done load's stops then say what was picked up: "Picked up 28 bags", "Picked up separately" for one whose pickup was logged on its own, or "Not picked up".
    - **Cancel This Load**, at the end (`#cancel`): a Confirm box, "Cancel the Sun, Nov 8 load", and Cancel Load. `POST /admin/map/loads/{load}/cancel` (`CancelTrailerLoadRequest`, which needs the box checked) marks it canceled, recording when and by whom, and goes to the Map page with "Canceled the Sun, Nov 8 load. Its 2 stops need scheduling again." The load stays, under Past loads.

    A done or canceled load has none of these, and changing one goes back to it with "This load is canceled, so it can’t be changed."
- **Everything** (`show=everything`): every contact whose current address has a location, for statistics and grant reporting: pickups in their colors, those in a planned load ringed in black with their load in the popup ("In the Sun, Nov 8 load · stop 2"), others in blue, and drop-off sites in gray, with counts above the map.
- **Search** (`q`, a name, phone number, or email, as Contacts searches; it takes the place of either view): up to 10 contacts found, on the map with the drop-off sites, each with the drop-off sites nearest first and their straight-line distance in miles.
- **A contact** (`contact`, their ID, from the address on their page; it takes the place of a view or search, and an unknown or deleted contact is a 404): that contact as a search shows each one (`MapReport::contact()`), with "Where Jamie Rivera is, with the drop-off sites." or "Jamie Rivera’s address isn’t on the map yet.", and no Start a Trailer Load button.

The map is drawn by `resources/js/admin-map.js`, which `app.js` loads only on this page, from the points in `#map-data`: Leaflet with OpenStreetMap's tiles and attribution. Without JavaScript, the lists still work. **Locate Addresses**, under it while any current address has no location (or a preview or an error is showing), lists current addresses without a location as JSON to copy for [addresses:geocode](02-services-and-commands.md#addressesgeocode-appconsolecommandsgeocodeaddressesphp), and takes the JSON it prints as `results` (`SaveLocationsRequest`, which refuses anything else with "Paste everything addresses:geocode printed, from the { at the start to the } at the end."): `POST /admin/map/locations` shows the page with a preview of each entry ([LocationImport](02-services-and-commands.md#locationimport-appserviceslocationimportphp)), and the locations it would save on the map in purple as "Not saved yet", and with `confirm` (the Save button) saves those it can and goes back to the map with "Saved 12 locations.". The servers never call a geocoder.

**Leaves (`/admin/leaves`)**, Leaves in the admin menu, shows the current season (`LeafLedgerReport`) as numbers linking to their lists: bags collected and logged pickups and drop-offs, both opening the Leaf Ledger, and the estimated bags of every pending application still waiting, opening Leaf Applications for all time. Under them, the 5 latest ledger entries of the season and the 5 latest applications, newest first, each followed by a button to its full page (Leaf Ledger and Leaf Applications). The menu's Leaves link stays current on every leaf page: the dashboard, Leaf Applications, an application, and the Leaf Ledger.

**Leaf Applications (`/admin/leaves/applications`)** lists applications like `leaves:applications`, with the same `period` filter and two filters the command doesn't have: `type[]` (`drop_off`, `pickup`, or both; none lists both) and `spam=1`, which adds test and spam applications. `/admin/leaves/applications/csv` takes the same query, except `spam`, and downloads `leaf-applications-<date>.csv` with the same columns as `leaves:applications --csv`. Each name links to the person's contact, once the application is linked. A Follow-up column, which the CSV and command leave out, shows each application's follow-up: Spam or Test for marked applications, Complete once its pickup or drop-off is logged, Not linked while it waits to be linked to a contact, or its follow-up group and why from `FollowUpReport`, such as "Waiting on us" and "No word from us in 9 days". A second line totals the listed applications' estimated bags and the bags still waiting for a pickup or drop-off, such as "180 bags estimated, 95 still waiting for a pickup or drop-off.", leaving out test and spam applications. A Leaf Ledger button beside the filters opens the Leaf Ledger, described below. `/admin/leaves/{application}` shows the same as a Follow-up line, except for a deleted application, and what `leaves:view` shows, including when the terms were accepted, with a notice for a deleted application; an unknown ID is a 404.

**An application's contact:** its page ends with the contact it's linked to ("Not linked to a contact." otherwise). When it needs review, a notice gives each reason, naming the other contacts it's about with links (`ApplicationReview::candidates()`), and says what to do. Mark Reviewed posts to `/admin/leaves/{application}/review`, which records which admin looked and when, shown afterwards as "Reviewed by Sam on Nov 5, 7:30 PM." "Move this application to" (or "Link this application to", when it isn't linked) posts the chosen `contact` to `/admin/leaves/{application}/contact` (`LinkApplicationContactRequest`): one of the contacts sharing its email or phone number, or `new` for a new contact made from it (`ApplicationReview::move()`). A contact that's deleted, or the one it's already linked to, is refused with an error. Both go back to the application with a message, such as "Moved application 43 to Jamie Rivera." A deleted application shows its contact without the forms, and posting to it is a 404.

**Test and spam applications:** the application's page ends with **Spam or Test** (`#mark`), a form posting `flag` (`spam` or `test`) and an optional `note` of up to 1,000 characters to `/admin/leaves/{application}/flag` (`FlagLeafApplicationRequest`; errors go back to `#mark`). `LeafApplication::flag()` records the admin and soft-deletes the application, closing its linked error logs (see [leaf_applications](01-database-schema.md#leaf_applications)), and the page returns with "Marked application 43 as spam." Marked applications show who marked them and when in a notice, plus an Unmark button posting to `/admin/leaves/{application}/unflag`, which restores them with "Unmarked application 43." Deleted applications without a mark have neither form, and posting to mark one is a 404. Contacts with only test and spam applications can be deleted from their edit page.

**Leaf Ledger (`/admin/leaves/ledger`)**, reached from the Leaves dashboard and the Leaf Ledger button on Leaf Applications, lists pickups and drop-offs logged on contacts' timelines and by marking trailer loads done (`LeafLedgerReport`), oldest first: the date, the contact's name linking to their page, bags, type, notes, and the admin who logged each entry. Deleted entries and entries of deleted contacts are left out. A line totals the season, such as "312 bags collected in Autumn 2026, from 41 pickups and 9 drop-offs." The `season` filter takes a season's autumn year, such as `2026`, from the first logged entry's season through the current one; anything else shows the current season. Seasons run July 1 to June 30 in Fort Collins time, so late deliveries count toward the autumn before. `/admin/leaves/ledger/csv` takes the same query and downloads `leaf-ledger-<season>.csv` with the same columns and full dates and times. Entries are read-only here.

**Error Logs (`/admin/errors`)** lists submissions of the donate and leaf application forms that didn't go through, like `submissions:list`, each name linking to the person's contact when one matches (`ContactReport::contactsFor()`), and each with its follow-up: whether the visitor submitted the same form successfully later, linking to the leaf application or donation it made, an admin closed it as resolved, a test, or spam, or neither (unresolved; see [Follow-ups](01-database-schema.md#form_submissions)). A Sign-Ins button beside the filters opens [Sign-Ins](#signing-in), and a red warning above them says when attempts to sign in failed in the last day. Its filters:

| Query | Values | Default | Like |
|-------|--------|---------|------|
| `period` | `30`, `90`, `365`, or `all`, like the other lists | `30` | `--days`, which defaults to 7 |
| `form[]` | `donation`, `leaf_application`, or both; none lists both | none | `--form` |
| `later` | `0` leaves out submissions the visitor got through with later | included | `--unresolved` leaves out both |
| `resolved` | `0` leaves out submissions an admin closed as resolved | included | |
| `spam` | `1` includes submissions closed as spam or a test | left out | `--spam-and-tests` |
| `all` | `1` includes submissions that succeeded | left out | `--all` |

The Submitted later and Resolved by an admin checkboxes are checked unless turned off, so the form sends a hidden `later=0` and `resolved=0` before each checkbox's `1`; when both arrive, the last one wins, as PHP reads query strings. `/admin/errors/csv` takes the same query and downloads `error-logs-<date>.csv` with the same columns as `submissions:list --csv`. `/admin/errors/{reference}` shows one submission in full, such as one a visitor quotes in an email, with a Contact line linking to the person's contact; an unknown reference is a 404.

**Closing errors:** the list's checkboxes with "Mark selected as" Spam, Test, or Resolved, or the Close Error form on a submission's page (which also takes a note of up to 1,000 characters), post the chosen references (`references[]`), `resolution`, and `note` to `/admin/errors/close`. It records which admin closed each one and when, then goes back to the page with a message such as "2 submissions marked as spam." or "1 submission marked as a test." Choosing none goes back with "Select at least one submission to mark."; every error shows at once. Closing one already closed replaces how it was closed. Reopen on a closed submission's page posts to `/admin/errors/reopen`, clearing all four resolution columns. Unknown references are skipped. Admin forms don't record their submissions in `form_submissions`, which is for following up with visitors.

For now the log holds form submissions only; it may grow into general error reporting.

The Period filter and its summary line, such as "No applications yet.", come from `App\Http\Controllers\Admin\Traits\FiltersByPeriod`, so every admin list offers the same periods.
